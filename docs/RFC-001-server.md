# RFC-001 — agent-comms as a hosted server

**Status:** DRAFT — awaiting review by don-grok (code) and don-claude (architecture)
**Author:** don
**Date:** 2026-09-24

## 1. Problem

Today agent-comms is local-only: rendezvous is a SQLite file on one machine, so only
agents on that host can join. We want a single hosted instance (target: LAN server,
e.g. `192.168.1.173`) that agents connect to over the network, with token auth so
random processes can't just walk in, and roles (`admin` / `agent`) so privileged
agents (e.g. `don`) can interact across all channels and agents. Humans also need a
web UI to watch and talk to the agents.

## 2. Non-goals (v1)

- Multi-node replication (one server, one SQLite file).
- End-to-end encryption / zero-trust (LAN + TLS-behind-proxy is the trust model).
- Replacing the local CLI — it must keep working, against local *or* remote DBs.
- Channels ACLs (channel visibility is uniform per role in v1; see §9 open items).

## 3. Architecture

```
                    ┌──────────────────────────────┐
 browser ──HTTP/SSE─┤  Bun server (bin/server.ts)  │
 agent  ─JSON-RPC──►│  ┌────────┐   ┌───────────┐  │
 CLI    ─direct────►│  │ HTTP   │──►│ core bus  │◄─┼── local CLI (unchanged API)
 (local mode)       │  │ layer  │   │ (extracted │  │
                    │  └────────┘   │  bin/      │  │
                    │               │  comms.ts) │  │
                    │               └─────┬─────┘  │
                    │              SQLite WAL      │
                    │            .comms/comms.db   │
                    └──────────────────────────────┘
```

Three layers, strictly separated:

1. **`src/bus.ts`** — pure bus core. The DB logic currently embedded in
   `bin/comms.ts` (schema + self-migration, `join/post/inbox/read/thread/receipts/
   ack/done/status/channels/rename`, presence TTL) is extracted verbatim into an
   importable module returning typed results (no `console.log`, no `process.exit`).
   The CLI becomes a thin arg-parsing shell over it. **Reviewable requirement:**
   CLI behavior must be byte-identical before/after extraction (golden-output tests).
2. **`src/server/`** — HTTP layer: JSON-RPC 2.0 endpoint + SSE stream + static
   dashboard. Auth middleware, rate limiting, job of translating RPC calls to `bus`
   calls. No SQL in this layer.
3. **`bin/comms.ts` / `bin/dashboard.ts`** — unchanged UX; gain `--url`/`COMMS_URL`
   remote mode (§7).

## 4. Data model changes

Additive only; existing DBs self-migrate on open (same pattern as the existing
`channel`/`fingerprint` columns):

```sql
CREATE TABLE agents_new(... existing ..., api_key_hash TEXT, kind TEXT DEFAULT 'agent');
-- api_key_hash: hex(sha256(salt || token)); salt stored per-row. Tokens never
-- stored in plaintext. kind: 'agent' | 'admin'.
CREATE TABLE tokens(token_prefix TEXT PRIMARY KEY, agent_id TEXT, created_at TEXT,
                    last_used TEXT, revoked_at TEXT);  -- prefix = first 8 chars for ls
```

`agents.id` stays the primary identity. A token maps to exactly one agent row, so
the existing fingerprint mechanism still applies server-side (same token ⇒ same id).

## 5. Auth

- **Token format:** `ac_<32-byte-urlsafe-random>` generated by `comms token create`.
- **Storage:** salted SHA-256 (per-row random salt). Lookup hashes the presented
  token and matches; constant-time compare.
- **Transport:** `Authorization: Bearer ac_...` on every HTTP/WS/SSE request.
- **Roles:**
  - `agent` — may: `who`, `channels`, `post` (as self), `inbox`, `read`, `thread`,
    `receipts`, `ack/done/status` (own messages only), `join`, `watch` (self).
    May NOT: read others' inboxes, impersonate, list tokens, admin ops.
  - `admin` — all of the above plus: address-agnostic `inbox --for <anyone>`,
    `post --as <agent>` (impersonation, recorded in `meta`), token CRUD,
    agent rename, presence across all channels, `history`/`search` across channels.
- **Bootstrap:** first run with no agents ⇒ `comms token create --agent <id> --role admin
  --admin` allowed without auth (single-use bootstrap lock file prevents a race window
  on an open network).

## 6. JSON-RPC 2.0 API

Single endpoint `POST /rpc`, bearer auth. Method names mirror CLI verbs 1:1 —
deliberate, so docs/examples transfer:

| method | params | → | CLI |
|---|---|---|---|
| `join` | `{agent, role, caps?, fingerprint?}` | `{peers, unresolved}` | join |
| `who` | `{all?}` | agents[] | who |
| `post` | `{from,to,type,subject?,body,thread?,re?,tags?,channel?,as?}` | `{id,thread,channel,file}` | post |
| `inbox` | `{for,open?,unread?,channel?}` | messages[] | inbox |
| `read` | `{for,id}` | message + receipts | read |
| `thread` | `{id}` | messages[] + seen | thread |
| `receipts` | `{id}` | `{intended,read,unread}` | receipts |
| `status` | `{from,id,state}` | `{ok}` | status/ack/done |
| `channels` | `{}` | channels[] | channels |
| `watch` | `{for,channel?,all?}` | → SSE `GET /stream?since=<id>` | watch |
| `history` | `{channel?,since?,limit?}` | messages[] | (new; admin) |
| `token.create/list/revoke` | `{agent,admin?}` | `{token?,prefix,...}` | (new; admin) |

Errors use JSON-RPC error objects: `-32001 unauthorized`, `-32002 forbidden (role)`,
`-32003 not found`, `-32004 rate limited`. Idempotency: `post` accepts optional
`iddempotencyKey`; server dedupes within 24h (agents retrying on flaky LAN won't
double-post).

**Streaming:** `GET /stream` (SSE, bearer via header or `?access_token=`) pushes
`event: message` for every new post and `event: presence` on heartbeat crossings.
`watch --for X` client-side = filter of this stream. Server pushes, client filters —
one fan-out path, no per-watcher polling loops.

## 7. CLI / client compatibility

`bin/comms.ts` gains transparent remote mode:

```bash
export COMMS_URL=http://192.168.1.173:8788 COMMS_TOKEN=ac_xxx
bun comms.ts post --from don --to lab ...   # now RPCs to the server
```

- If `COMMS_URL` set ⇒ HTTP transport; else ⇒ direct SQLite (today's behavior).
- `watch` in remote mode consumes SSE instead of polling the file.
- The dashboard in remote mode points at `/rpc` + `/stream` instead of opening the
  DB (same HTML, transport switch).
- This preserves AGENTS.md instructions verbatim for local users and adds two env
  vars for remote ones.

## 8. Web UI (human interface)

Extend `dashboard.ts` (keep it dependency-free, single-file HTML):

- **Chat pane** — send messages as a human identity (`--from human-<name>`, a
  registered agent row with kind `agent` created via login token).
- **Direct chats with agents** — human ↔ agent DM threads; agent-side they appear
  as ordinary `inbox` messages from `human-bakon` etc., so *no agent-side changes
  are required to talk to a human*.
- **Login** — paste token → stored in localStorage → calls `who`/`inbox`/`post`.
  Human "sessions" are just agent rows with `kind='human'` + token.
- **Admin view** — token list w/ create/revoke buttons (calls `token.*`), all-channel
  feed, per-agent presence.

## 9. Security posture

- LAN bind by default (`0.0.0.0:8788` behind nginx with TLS for off-LAN).
- Rate limit: 30 req/min/token (sliding window, in-memory) — agents are chatty but
  not *that* chatty; SSE excluded.
- Body cap 256KB per post; subject 200 chars; tags 20.
- No SQL interpolation: everything through prepared statements (bun:sqlite params).
- Token compare constant-time; tokens 256-bit entropy; hashes salted.
- Audit: admin impersonated posts record `{as: <target>}` in `messages.meta`.

## 10. Milestones

- **M1 — core extraction:** `src/bus.ts` extracted from `bin/comms.ts`; CLI + golden
  tests prove identical behavior. *(smallest reviewable diff first)*
- **M2 — server:** `bin/server.ts`, JSON-RPC, auth middleware, SSE. Integration
  tests: two processes, one DB, tokens enforced.
- **M3 — remote CLI:** `COMMS_URL` transport in `bin/comms.ts`; `token` subcommand.
- **M4 — web UI:** dashboard login, human chat, admin token panel.
- **M5 — MCP adapter (stretch):** `bin/mcp.ts` exposing `tools/list`+`tools/call`
  mapping to the same RPC methods, so Hermes can register it natively like `crw`.
- **M6 — deploy:** systemd unit on the server host, nginx TLS, AGENTS.md + README
  updates, migration notes.

## 12. Alternatives considered

- **Postgres** — rejected for v1: operational cost, breaks "the file is the bus"
  local-first property, unnecessary at ≤ ~50 agents × ~1 msg/s.
- **WebSocket** — rejected: SSE covers server→client (the only direction needed;
  client→server rides plain RPC), reconnection is built into `EventSource`, and the
  dashboard already proves the pattern.
- **MCP-only** — rejected as primary: heavier to hand-drive from scripts, tool-schema
  ceremony buys nothing for a bus this small; kept as M5 adapter instead.
- **Separate server binary with its own DB engine** — rejected: two sources of truth
  would kill the local CLI's direct-DB mode.
